# Botping

Сервис на Python: двухуровневый мониторинг ваших Telegram-ботов. **Основная проверка** — периодический `getUpdates`-зонд к каждому включённому боту (HTTP 409 Conflict означает, что кто-то уже ведёт long-polling, то есть бот реально жив; HTTP 200 ok=true означает, что никто не поллит, бот мёртв). **Вторичная проверка** — один `getMe` к токену admin-бота, показывающий глобальную доступность самого Telegram API с VPS Botping. История проверок и инциденты пишутся в SQLite, при серии неудач отдельный админ-бот шлёт уведомления в указанные `chat_id`. Все параметры мониторинга и **список ботов** настраиваются в Telegram (меню «Боты» / «Настройки»), в том числе **добавление нового бота**: «Боты» → «+ Добавить бота» → имя → токен (валидность токена проверяется через `getMe` перед сохранением).

## Требования

- Python 3.11+
- Токен админ-бота от [@BotFather](https://t.me/BotFather)
- Ваш числовой `chat_id` (можно узнать у [@userinfobot](https://t.me/userinfobot))

## Установка локально

```powershell
cd d:\BOTS\Botping
python -m venv .venv
.\.venv\Scripts\activate
pip install -e .
copy .env.example .env
# отредактируйте .env
python -m botping.main
```

Переменные см. [.env.example](.env.example). Файл БД по умолчанию: `./data/botping.db` (каталог создаётся автоматически).

## Docker

```bash
cp .env.example .env
# заполните ADMIN_BOT_TOKEN и ADMIN_CHAT_IDS
docker compose up -d --build
```

База хранится в volume `botping_data` (путь внутри контейнера `/app/data`).

## VPS (systemd)

Пример юнита: [deploy/botping.service](deploy/botping.service). Создайте пользователя `botping`, виртуальное окружение в `/opt/botping/venv`, скопируйте проект в `/opt/botping`, укажите `EnvironmentFile` с секретами. Права на файл БД только у пользователя сервиса.

## Команды и меню в Telegram

Доступ только для `ADMIN_CHAT_IDS`.

- `/start` — главное меню
- `/status` — последние проверки и открытые инциденты
- `/failures` — сбои за последние 7 дней; `/failures 2026-04-01 2026-04-14` — за диапазон дат
- `/settings` — параметры (интервал, таймаут, порог падений, повтор алерта, медленный ответ, **проверка Telegram API (0/1)**, **ежедневный Excel в 00:00 по Москве (0/1)**, тихие часы JSON)
- **Боты** — список, включение/выключение, удаление, **добавление нового бота** пошагово (имя и токен)

Токены в ответах маскируются. Полный токен хранится в SQLite — защитите файл БД.

## Поведение мониторинга

- **Как работает проверка.** На каждом тике Botping делает по одному `getUpdates`-зонду (POST, `timeout=0, offset=-1, limit=1`) на каждый включённый бот. `offset=-1` не сдвигает внутренний курсор update_id — это безопасно для уже работающего бота. Интерпретация ответа: `409 Conflict` → бот жив (кто-то уже ведёт long-poll); `200 ok=true` → никто не поллит, бот помечается как недоступный; сетевая ошибка/таймаут/5xx → сам Telegram API нам недоступен, и такой тик **не учитывается** в счётчик падений бота (это фиксирует отдельная проверка Telegram API).
- **Ограничение.** Метод подходит только для ботов на long polling. **Webhook-боты** не держат `getUpdates`, поэтому зонд будет ошибочно возвращать «бот мёртв» — такие боты лучше выключать в меню «Боты».
- **Ложные срабатывания.** Момент между long-poll-итерациями работающего бота теоретически может совпасть с нашим зондом — тогда он коротко увидит `ok=true`. Параметр `fail_threshold` (по умолчанию 2) гасит подобные единичные глюки.
- **Telegram API-проверка.** Раз в тик делается `getMe` к токену admin-бота. Отдельный инцидент «Telegram API недоступен» открывается/закрывается независимо от per-bot инцидентов. Выключается параметром `telegram_api_probe_enabled=0`.
- **Ежедневный Excel:** в меню «Настройки» пункт «Ежедневный Excel 00:00 МСК» — введите `1`, чтобы каждую полночь по календарю **Europe/Moscow** во все чаты из `ADMIN_CHAT_IDS` уходил тот же Excel, что и по `/report`, за **предыдущие сутки**. `0` — выключено (по умолчанию). Если процесс долго не работал, при следующем запуске возможна **догонка**: по одному файлу на каждый пропущенный день до «вчера» включительно.
- Ответ `429` от API **не увеличивает** счётчик «падений» для инцидента (считается rate limit).
- **Тихие часы**: новые и повторные алерты при down подавляются; сообщение о **восстановлении** всегда отправляется.
- Настройки читаются из БД на каждом цикле — изменения из Telegram применяются без перезапуска.
